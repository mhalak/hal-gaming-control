Version declaration, CI, package build and successful deployment on the actual host are **separate facts**. A changed Git file or manifest does not prove that any HA instance or Windows PC installed it. Record the exact reviewed source SHA, package hash, previously working release, and real device smoke-test results before deploying. Never reuse a release tag or silently overwrite a published artifact.

## Prepare a version

1. Edit the root release.json once, preserving unrelated component versions.
2. From the repository root run `python tools/release_identity.py sync-ha` to synchronize the tracked HA manifest's version, and review the diff. Run `python tools/release_identity.py check`. The Windows CI test suite checks this consistency on both platforms.
3. Commit the declaration, generated manifest if changed, and release notes; wait for the existing CI gates. Do not prepare a candidate from an unreviewed branch or dirty checkout.
4. On a trusted Windows build host use a fresh checkout of the exact reviewed commit, verify the tree and invoke `windows_agent/build.ps1`. The script emits version.txt and build-info.json into the complete agent onedir package only after successful builds and source identity verification. Explicit Version is optional and is an assertion, not an override.
5. For a manual HA deployment, run `python tools/release_identity.py stage-ha --output /absolute/path/outside/repo/hal_gaming_control` from the exact reviewed **clean** checkout. The output directory must not exist beforehand and must be outside the checkout. It contains the tracked HA component files, manifest and a generated `build-info.json` with the exact source SHA. Install the entire staged component directory as `custom_components/hal_gaming_control` in HA, after separate authorization and backup; do not stage directly over an existing live integration. Check integration reload/restart and rollback. For HACS/plain source installs without generated `build-info.json`, version comes from the local manifest and SHA remains **unknown**; never infer a runtime SHA from local Git or a different workstation. The optional `identity --component home_assistant` command still prints external provenance for records, but does not stamp an installed package.
6. Record artifact SHA-256, resolved dependencies/toolchain, service path, observed version, exact source SHA, previous known-good version and rollback path. Preserve config/Recorder. Both PCs should receive the same verified package.

The Windows Agent version diagnostic reports the last validated discovery metadata and its SHA (if supplied by a supported package); the HA integration version diagnostic reads its installed manifest and only reports a SHA from a matching staged build-info.json. Both sensors are diagnostics, not evidence of an online process. The Git SHA is source provenance metadata, not a cryptographic attestation of the binary, reproducibility, authenticity, or live process state. Git status ignores ignored files: use fresh isolated trusted source/build environments without ignored source overrides. Do not ship failed-build output. No public unsigned Windows binaries, automated Windows publishing, remote update activation or Windows-only GitHub Releases in this HACS repository. The separate operator-triggered, SHA/CI-gated HA-only GitHub versioned release workflow is described in [HACS release policy](hacs_release.md); it never deploys to a live HA or Windows host. See [HACS release policy](hacs_release.md) and [Windows deployment](windows_deployment.md).

## Mandatory versioning and deployment evidence

- **Every deployable code change** requires a version increment for each *affected distributable component*, based on SemVer intent: PATCH for backward-compatible fixes and packaging/diagnostics, MINOR for new capabilities or an intentionally revised pre-1.0 UI/behavior, MAJOR for incompatible stable interfaces once 1.0 exists. Unchanged components do not increment merely because another component deploys.
- A deployment to an already installed version must have **exact matching source SHA/package hash**; a changed build may never be reused under the same version. Allocate versions in `release.json`, synchronize the HA manifest and update tests/release notes **before** building; use CI and reviewed main checkout as gates.
- Pixie must record each TrueNAS HA instance or Windows PC in private deployment evidence: target (private), old/new version, build-info Git SHA and package SHA-256 where available, source ref, start/end result, validation checks and rollback backup location. The public issue #56 receives **sanitized status only** (candidate / deployed / skipped / blocked / rolled back).
- **Success = confirmed installed/running version and verified functionality on the intended host**, not a GitHub merge, green CI or version declaration. If a service reports an older version, compare actual executable/tree hashes and live MQTT metadata before deciding to rebuild, restart or roll back. Never edit `version.txt` alone as a fake fix.
