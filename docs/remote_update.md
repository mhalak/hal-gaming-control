# Remote update development preview

The agent still has exactly three gaming sensors and two gaming actions. Separate administrative MQTT topic command/update is disabled by default. Enable only with a provisioned updater scheduled task, pinned Ed25519 public key, and a trusted fixed HTTPS release mirror. The mirror is expected to be operated by the SmartHouse server; private GitHub credentials are never sent to PCs. Mirror manifest/signature/ZIP byte-for-byte. No arbitrary URL or executable in MQTT commands.

Payload: {"version":"0.2.0","request_id":"<canonical UUID>","expires_at":<Unix seconds within next 120 seconds>}. The command is non-retained. Only strictly newer numeric versions. Broker ACL must reserve command/update for trusted deployment operators; ordinary action publishers do not need it. Agent submits an exclusive protected request file and starts a fixed SYSTEM scheduled task. Task validates request, downloads and verifies the signed version, filename, SHA256, and byte length, rejects unsafe archives, then stops service, swaps program folder, starts and waits for health for the same request ID: confirmed running service plus a real QoS 1 MQTT PUBACK. Failed start or health causes rollback and verification of the restored version. Config and logs are untouched. The updater lives outside the agent folder and is not self-updated.

Status is stored durably and published at QoS 1 by a separate updater MQTT client ID, so progress can continue while the agent service is stopped; terminal status is retried after reconnect. Keep the release signing key offline or in a protected GitHub environment. Do not publish unsigned packages. The journal, previous installation, and recovery evidence are retained until the new version is verified; failed recovery preserves them for an administrator. The Python transaction, validation, status, and simulated power-loss paths are covered by automated tests. Native Windows service/task/ACL behavior and real broker reconnect behavior remain NOT VERIFIED until exercised on a disposable Windows VM. No real deployment or signing credentials are configured.

## Signed releases
Manual Signed Windows release workflow runs on main only; tests/build before signing. Configure the protected GitHub environment windows-release with a review gate and secret WINDOWS_RELEASE_SIGNING_KEY (Ed25519 PEM). Provision matching public key on each PC independently, not from an unverified download. Release creates windows-vX.Y.Z with two ZIPs and detached signed JSON manifests: windows-install-X.Y.Z.zip (first install includes both executables and PowerShell scripts) and windows-agent-X.Y.Z.zip (agent-only update). Mirror the latter ZIP, JSON and SIG unchanged under the configured HTTPS base. Signing is not enabled until the owner provisions keys and mirror. Publish only reviewed main commits and never reuse versions. Releases are not automatically pushed to PCs. CI tests packaging and signed manifest compatibility; full workflow requires signing credentials.

## Transaction recovery hardening
The scheduled task also runs at Windows startup. Durable transaction phases download/swap/committed allow interrupted downloads to be abandoned and interrupted swaps to restore the previous version; a committed transaction only cleans up. Status is published best effort by a separate MQTT client even when the agent is stopped and retained in a protected file. Agent health uses a fresh QoS 1 PUBACK and running-service verification. Update request IDs are persisted through their expiry window. Power-loss semantics and ACLs still require real Windows testing; failed recovery preserves evidence for an administrator.
