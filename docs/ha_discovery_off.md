# HA scoped MQTT discovery — legacy baseline / HA 0.7.0 clean installation

See [the breaking 0.7.0 clean-cut procedure](domain-clean-cut.md) before installing the new package on a HA instance with an existing integration.

Install custom_components/hal_gaming_control in HA configuration/custom_components (or HACS custom repository where private repository access is supported). Restart HA. MQTT and Recorder must be enabled. The agent advertises metadata and the five native MQTT entities; HA creates a separate custom config entry per device, either through automatic MQTT discovery or manually: Settings > Devices & services > Add integration > SmartHouse Parental Control. The manual step listens for a few seconds on SmartHouse/Gaming/+/discovery through the mqtt integration and offers the PCs not yet configured, so the global MQTT discovery option (and other publishers' homeassistant/* discovery topics) is not touched; it can stay disabled. If no new PC is found the flow reports no_devices_found. Confirm the entry. Restrictions are OFF by default. When HA global MQTT discovery is disabled, this integration creates the three raw sensors and two advertised action buttons itself using only per-device MQTT topics; Recorder resolves these custom entity IDs. When native discovery is enabled it uses existing MQTT entities instead. Do not change the global discovery setting after onboarding without planning entity/history migration.

The following describes 0.4.2 legacy controls; planned additive Weekend bonus and automation-only enforcement are in [product direction](product_direction.md).

Use device page Configuration sliders (-10 for disabled/fallback, 0–600 minutes otherwise, step 10) and Add/Remove action selectors. Add 30 minutes in Controls extends only today's daily quota, expires at local midnight. The Options Flow provides a menu. Restrictions and schedule, MQTT configuration, + Add action (only unselected supported agent capabilities), remove action, move action to first position, Save. MQTT actions execute in selected order, best effort; no lock acknowledgement. Save commits the options; gaming settings apply live except catalog/device metadata changes. Quotas: local calendar day and Mon–Sun week; Saturday/Sunday each use the weekend daily override when set. No combined weekend quota. The -10 slider value maps to the stored -1 sentinel (disabled/fallback); 0 disallows play. Any applicable limit or schedule violation triggers the configured actions while a game is running; retry every 15 s while still violated. The rule engine is pure Python. Controls use either native MQTT discovery buttons (enabled mode) or direct integration buttons (disabled mode), never both from this integration. 

Uses current_game and uptime sensor Recorder history (lookup by the selected native MQTT or direct integration entity IDs), integrating intervals from start of week, then live state change events. Concurrent games count once overall and individually for each game. Offline intervals marked unavailable do not count; HA/Recorder/broker downtime is bounded by uptime-heartbeat coverage, so unobserved time does not count (semantics and limits: docs/recorder_coverage.md). History before the retention window or excluded entities is incomplete; ensure both current_game and uptime are recorded with at least 8 days retention. Integration does not backfill offline data. HA restart/Recorder lag, DST, native discovery compatibility and real HA options flow require acceptance testing. This is not a tamper-proof controller. If HA/MQTT are down, rules cannot execute.

The per-device Unlimited gaming switch is a persistent, HA-local override of all automatic restrictions; it does not reload the integration or reset accounting. The integration exposes three raw telemetry entities, two gaming action buttons and a separate administrative update entity. Two derived sensors expose remaining daily and weekly budgets in percent, with weekend daily override and unknown for disabled/unlimited quotas. All other statistics and restriction state remain internal; configure through the integration's Options flow.

Acceptance: confirm auto-discovery, one shared HA device, options save and reload, action uniqueness/order, no enforcement when disabled, time quotas spanning midnight/weekend, simultaneous games, offline/unknown history, restart/reconnect without false lock, re-open after limit, no duplicate HA entities. Validate on a disposable Windows game session. Core manual actions have passed maintainer smoke testing; full acceptance remains outstanding. CI tests pure rule/protocol logic and checks syntax; HA runtime tests and real Windows acceptance remain required.

## Command freshness
Enforcement waits for an observed change of the existing uptime sensor after HA startup/reload or unavailable state. A retained baseline is insufficient. Heartbeat older than 90 seconds suppresses enforcement until another uptime value arrives. This can delay enforcement by roughly one 60-second heartbeat after reconnect/configuration; it does not introduce local policy or new sensors. The freshness gate protects actions; historical accounting is bounded separately by heartbeat coverage (docs/recorder_coverage.md). Verifying that behaviour against a real HA restart remains a deployment acceptance step. CI includes actual HA Config/Options flow tests using a pinned HA test harness; real broker/service, Recorder restart and lock/termination still require acceptance tests.
